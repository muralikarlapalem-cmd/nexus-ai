NEXUS AI System Architecture

Multi-agent IT service intelligence platform: FastAPI, LangGraph agents, hybrid RAG, Celery, React

1. Summary

NEXUS AI is an IT service desk in which LLM agents work support tickets. A user files a ticket in the React app. An agent or admin starts a run, and a LangGraph supervisor, executing inside a Celery worker, passes the ticket through a Triage agent, an optional Security agent, a Diagnosis agent and a Knowledge agent. Any of them can pause the run for human review.

The agents ground their answers in a knowledge base of runbooks and resolved tickets, searched with hybrid retrieval: dense vectors in Qdrant plus BM25 keywords, merged with reciprocal rank fusion and reranked by a cross-encoder. When a diagnosis is confident, the Knowledge agent writes it up as a new runbook and adds it to the knowledge base, so the system improves as tickets are resolved.

Tickets can also come from ServiceNow; the result goes back as a work note. People sign in with Keycloak, and personal data is redacted before it is stored or sent to the LLM. Everything runs locally under Docker Compose; the LLM and, by default, the embeddings come from the OpenAI API.

3. Ticket lifecycle, end to end

The sequence below follows one ticket from creation to resolution, including the optional human-review pause. Steps 3–5 are asynchronous: the API returns as soon as the Celery task is queued, and the client polls for progress.

Figure 2. Sequence for one ticket. Dashed arrows are responses. In step 3 the API marks the ticket in_progress before queueing, so a second run is refused. In step 6, a ticket whose text matches an injection pattern is assigned to a human and the run stops before any LLM call. Approve and resolve and Reject (12–14) need no agent, so they finish inside the request; sending the ticket back to an agent instead (API only, next_agent) is queued as resume_ticket_task. While a run is going it refreshes a heartbeat in Redis at every step. If OpenAI can't be reached, step 5 is retried after 1, 2 and 4 minutes; a run that dies without a word (power cut, worker restart) is handed to a person within about 7 minutes, and Retry agents starts it again. A ticket imported from ServiceNow enters at step 2 through the sync job instead of steps 1–3; see section 10.

Ticket status lifecycle

Manual status changes go through POST /tickets/{id}/status, which rejects any transition not in VALID_STATUS_TRANSITIONS and writes a ticket_status_history row with the user and reason. The agent pipeline sets in_progress and resolved directly on the model.

SLA windows are set at creation from the priority: critical 4 h · high 8 h · medium 24 h · low 72 h. A Beat job flags breaches every 15 minutes.

4. Agent orchestration

The supervisor is a LangGraph StateGraph over a shared TicketState. Every node returns the full state with next set; one routing function reads it after each node. If iteration has reached 8, the router sends the run to guard, which ends it with an error for manual review. State is checkpointed in Redis with the ticket ID as the thread ID.

Figure 3. Supervisor graph. *Triage escalates on data-loss risk, a production outage over 1 h, a security breach, or confidence below 0.4. Before START, run_supervisor re-checks the ticket text for prompt injection and hands matches to a human instead of running the graph. The resume API can still send an approved ticket back to an agent with next_agent; the app's review panel does not offer this.

5. RAG pipeline

Retrieval combines two complementary signals. Dense vectors find passages with similar meaning, even with different wording. BM25 finds exact terms such as error codes, hostnames and product names that embeddings tend to blur. The two ranked lists are merged with reciprocal rank fusion, then a cross-encoder rereads each candidate together with the query to pick the best few.

Query path

Query/rag/query, /rag/query/stream or the rag_search tool; personal data redacted
→
Embedsame model as ingestion
→
RetrieveQdrant top 10 (tenant, type, category filters) + BM25 top 10
→
RRF fusescore = Σ 1/(60 + rank); keep 20
→
Rerankcross-encoder scores each (query, chunk) pair; keep 3
→
Generatecontext-only prompt with numbered, cited sources

Ingestion path

Sourcessample runbooks, raw text, PDF / Markdown uploads, resolved tickets, agent runbooks
→
Load + redactdocuments + metadata; personal data removed (Presidio)
→
Chunk512 tokens, 64 overlap; header-aware; drops chunks under 50
→
EmbedOpenAI 1536-d or Ollama 768-d
→
IndexQdrant upsert with deterministic chunk IDs; BM25 add

Why reciprocal rank fusion

Cosine similarity and BM25 scores live on unrelated scales, so adding them directly is meaningless. RRF uses only each document's rank in each list. A chunk ranked 2nd by vectors and 3rd by BM25 scores 1/62 + 1/63 ≈ 0.032, beating a chunk ranked 1st by only one retriever (1/61 ≈ 0.016). Agreement between retrievers is rewarded without any tuning.

Feedback loop

The knowledge base grows from three automatic sources: the Knowledge agent's generated runbooks (immediately), resolved tickets (Beat job every 6 hours, up to 200 at a time), and the weekly BM25 rebuild from Qdrant, which keeps the keyword index consistent with the vector store across restarts.

PostgreSQL holds the system of record. Agent outputs are stored as JSONB on the ticket so their schema can evolve without migrations. Schema changes go through Alembic; in development the API also auto-creates tables at startup.

7. Security and access control

Authentication

The token's own header decides how it is checked. Keycloak tokens (RS256) come from the web app's sign-in with authorization code + PKCE (public client nexus-frontend). The API checks signature (realm keys, fetched again only for an unknown key ID), expiry, issuer (the nexus realm by its browser or Docker address) and audience (nexus-backend). The first sign-in creates the NEXUS user, or links a local account with the same e-mail if Keycloak verified it. The role follows the realm roles nexus-admin / nexus-agent / nexus-analyst on every request. Local HS256 tokens from /auth/login never call Keycloak; refresh tokens are refused as access tokens. Local sign-in and self-registration (always role user) are refused when APP_ENV=production. CLI: make-admin, sso-setup, sso-user, sso-check.

8. Background processing

Celery is configured for long, reliable tasks: messages are acknowledged only after a task finishes (acks_late), re-queued if a worker dies, and handed out one at a time (prefetch_multiplier=1). Tasks wrap async code in a fresh event loop and dispose of the database pool afterwards, so asyncpg connections never leak across loops. The Qdrant async client is likewise recreated whenever the event loop changes.

Observability

  • Metrics: the API serves /metrics; the worker's 4 processes share theirs (multiprocess mode) on :9101. Tickets by source, agent runs by outcome and time, AI query time, integration syncs, PII redactions, HTTP traffic. Known series start at 0 so the first event shows.
  • Traces: OpenTelemetry spans for API requests and database queries → Jaeger (Zipkin JSON). LangSmith traces every agent run, named after the ticket and linked from its page.
  • Logs: loguru with request IDs; Alloy ships every nexus-* container's output to Loki. An "error line" needs an error marker (| ERROR |, ERROR/, FATAL:, tracebacks, LOGIN_ERROR); database query logging is ignored.
  • Health: /health/ liveness, /health/ready checks DB and Redis, /health/info.

Evaluation and CI

GitHub Actions runs migrations, pytest and ruff against Postgres and Redis service containers. On main, an eval gate runs RAGAS with thresholds of faithfulness 0.75, answer relevancy 0.70, context recall 0.65 and context precision 0.60; the agent eval requires 70 % triage accuracy.

Rejected runs and runs stopped by the guard stay open and go to a human instead of being marked resolved. Resuming a ticket with no paused run returns 409.

Self-registration accepted any role. /auth/register now always creates a user and rejects a role field; the first admin is promoted with the make-admin CLI command, which writes an audit-log entry.

CI eval gate used the wrong key. The workflow now passes OPENAI_API_KEY, which the code actually reads.

Failing chunker test. test_chunk_id_is_deterministic now uses text longer than min_chunk_size; the full suite passes (181 tests as of 19 Nov 2026).

Web search blocked; sources not recorded (commit e426043). The DuckDuckGo tool was rate-limited and its error text reached the LLM as if it were results.
