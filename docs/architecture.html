NEXUS AI System Architecture

Multi-agent IT service intelligence platform: FastAPI, LangGraph agents, hybrid RAG, Celery, React

1. Summary

NEXUS AI is an IT service desk in which LLM agents work support tickets. A user files a ticket in the React app. An agent or admin starts a run, and a LangGraph supervisor, executing inside a Celery worker, passes the ticket through a Triage agent, an optional Security agent, a Diagnosis agent and a Knowledge agent. Any of them can pause the run for human review.

The agents ground their answers in a knowledge base of runbooks and resolved tickets, searched with hybrid retrieval: dense vectors in Qdrant plus BM25 keywords, merged with reciprocal rank fusion and reranked by a cross-encoder. When a diagnosis is confident, the Knowledge agent writes it up as a new runbook and adds it to the knowledge base, so the system improves as tickets are resolved.

Everything runs locally under Docker Compose. The LLM and, by default, the embeddings come from the OpenAI API. Ollama is available for local embeddings and hosts an optional fine-tuned model.

Ticket status lifecycle

Manual status changes go through POST /tickets/{id}/status, which rejects any transition not in VALID_STATUS_TRANSITIONS and writes a ticket_status_history row with the user and reason. The agent pipeline sets in_progress and resolved directly on the model.

4. Agent orchestration

The supervisor is a LangGraph StateGraph over a shared TicketState. Every node returns the full state with next set; one routing function reads it after each node. If iteration has reached 8, the router sends the run to guard, which ends it with an error for manual review. State is checkpointed in Redis with the ticket ID as the thread ID.

Figure 3. Supervisor graph. *Triage escalates on data-loss risk, a production outage over 1 h, a security breach, or confidence below 0.4. Before START, run_supervisor re-checks the ticket text for prompt injection and hands matches to a human instead of running the graph.

5. RAG pipeline

Retrieval combines two complementary signals. Dense vectors find passages with similar meaning, even with different wording. BM25 finds exact terms such as error codes, hostnames and product names that embeddings tend to blur. The two ranked lists are merged with reciprocal rank fusion, then a cross-encoder rereads each candidate together with the query to pick the best few.

Query path

Query/rag/query, /rag/query/stream or the rag_search agent tool
→
Embedsame model as ingestion
→
RetrieveQdrant top 10 (tenant, type, category filters) + BM25 top 10
→
RRF fusescore = Σ 1/(60 + rank); keep 20
→
Rerankcross-encoder scores each (query, chunk) pair; keep 3
→
Generatecontext-only prompt with numbered, cited sources

Ingestion path

Sourcessample runbooks, raw text, PDF / Markdown uploads, resolved tickets, agent runbooks
→
Loaddocuments + metadata (source type, category, tenant)
→
Chunk512 tokens, 64 overlap; header-aware; drops chunks under 50
→
EmbedOpenAI 1536-d or Ollama 768-d
→
IndexQdrant upsert with deterministic chunk IDs; BM25 add

Why reciprocal rank fusion

Cosine similarity and BM25 scores live on unrelated scales, so adding them directly is meaningless. RRF uses only each document's rank in each list. A chunk ranked 2nd by vectors and 3rd by BM25 scores 1/62 + 1/63 ≈ 0.032, beating a chunk ranked 1st by only one retriever (1/61 ≈ 0.016). Agreement between retrievers is rewarded without any tuning.

Feedback loop

The knowledge base grows from three automatic sources: the Knowledge agent's generated runbooks (immediately), resolved tickets (Beat job every 6 hours, up to 200 at a time), and the weekly BM25 rebuild from Qdrant, which keeps the keyword index consistent with the vector store across restarts.

6. Data model

PostgreSQL holds the system of record. Agent outputs are stored as JSONB on the ticket so their schema can evolve without migrations. Schema changes go through Alembic; in development the API also auto-creates tables at startup.

users

id PK · email, username unique · full_name · role (admin | agent | analyst | user) · keycloak_id unique · is_keycloak_user · hashed_password (local only) · is_active · timestamps, last_login_at

id PK · ticket_id → tickets · old_status, new_status · changed_by_id → users · reason · changed_at

id PK · user_id → users · action · resource_type, resource_id · details JSONB · trace_id, span_id, request_id · ip_address, user_agent · timestamp

Other stores. Redis: db0 LangGraph checkpoints (one thread per ticket), db1 Celery broker, db2 task results (24 h expiry). Qdrant: collection nexus_knowledge, payload carries tenant_id, source_type, category and source names. BM25: pickled index on local disk.

7. Security and access control

Authentication

The API accepts two kinds of Bearer token. Keycloak tokens are verified against the realm's JWKS endpoint; on first use a matching local user is created automatically from the token's email and username. Local HS256 tokens from /auth/login are the development fallback, with refresh tokens valid for 7 days and access tokens for 60 minutes. Self-registration is refused when APP_ENV=production; elsewhere it always creates a user (a role field is rejected with 422). The first admin is promoted from the server shell with python -m app.cli make-admin <username>.

8. Background processing

Celery is configured for long, reliable tasks: messages are acknowledged only after a task finishes (acks_late), re-queued if a worker dies, and handed out one at a time (prefetch_multiplier=1). Tasks wrap async code in a fresh event loop and dispose of the database pool afterwards, so asyncpg connections never leak across loops. The Qdrant async client is likewise recreated whenever the event loop changes.

This is a development topology: source is bind-mounted with auto-reload, and Keycloak runs in dev mode. A production deployment would build immutable images, run Keycloak in production mode with its own database, and put TLS and a reverse proxy in front of the API.

Observability

  • Logs: loguru, one line per request with method, path, status, duration and X-Request-ID (also returned as a header).
  • Tracing: LangSmith tracing is enabled through LANGCHAIN_TRACING_V2; the ticket column langsmith_run_id is never filled.
  • Metrics: Prometheus counters and histograms (tickets created, agent runs, RAG latency, eval scores) are defined but not exposed or recorded.
  • Health: /health/ liveness, /health/ready checks DB and Redis, /health/info.

Evaluation and CI

GitHub Actions runs migrations, pytest and ruff against Postgres and Redis service containers. On main, an eval gate runs RAGAS with thresholds of faithfulness 0.75, answer relevancy 0.70, context recall 0.65 and context precision 0.60; the agent eval requires 70 % triage accuracy.

10. Known gaps and recommendations

Found while reviewing the code on 15 Nov 2026. Severity reflects impact on correctness or security, not effort.

SeverityGapRecommendation
MediumEval scores below CI thresholds. The latest local RAGAS run scored below all four thresholds, so the gate on main will fail.Re-run evals after the reranker fix; improve retrieval or ground-truth data before enforcing the gate.
MediumPII redaction not applied. Personal data in tickets goes to the LLM and into the knowledge base as written.Call redact_pii before storage or ingestion.
MediumInjection guard is pattern-only. Rephrased attacks pass, and fetched web and NVD text is not checked.Wrap untrusted text in delimiters in every agent prompt and instruct the model to treat it as data.
MediumResume loop. An approved review defaults to diagnosis_agent; if diagnosis escalates again the run cycles until the guard stops it at 8.Record that a human approved and skip re-escalation for the same reason.

Recently fixed

Reranker starved of candidates (commit ef25668). Hybrid search previously cut the fused list to 3 before reranking, so the cross-encoder could only reorder those 3. It now receives up to 20 candidates (rerank_candidates) and selects the best 3.

Prompt-injection guard wired in (commit b8a4c8e). The existing pattern check now runs on every API path that sends text to the LLM or the knowledge base, and again in run_supervisor before any agent runs.

Results lost after human review (commit d255a28). A shared persist_final_state() now saves the outcome after the first run and after every resume. Rejected runs and runs stopped by the guard stay open and go to a human instead of being marked resolved. Resuming a ticket with no paused run returns 409.

Self-registration accepted any role. /auth/register now always creates a user and rejects a role field; the first admin is promoted with the make-admin CLI command, which writes an audit-log entry.

CI eval gate used the wrong key. The workflow now passes OPENAI_API_KEY, which the code actually reads.

Failing chunker test. test_chunk_id_is_deterministic now uses text longer than min_chunk_size; the full suite passes (61 tests as of 16 Nov 2026).

Web search blocked; sources not recorded (commit e426043). The DuckDuckGo tool was rate-limited and its error text reached the LLM as if it were results. Tavily now runs only when the knowledge base has no good match, failures are stated plainly, and each diagnosis saves the internal documents or web URLs it used.

RAG failed after a worker's first task (commit e426043). The Qdrant async client was a process-wide singleton, but each Celery task runs on a new event loop, so later searches failed with "Event loop is closed". The client is now recreated per loop.

Outdated status test (commit aa0fc39). test_change_ticket_status now follows the allowed lifecycle, and a new test checks that skipping straight from open to resolved is rejected.
